## 1. Extensions installieren

Öffne in VS Code die Extensions-Ansicht:

> **Menü links: das vier Quadrate-Symbol** oder `Strg+Shift+X`

Suche und installiere der Reihe nach diese drei Extensions (je: **Install** klicken, danach ggf. **Reload**):

- [x] **Portable Kanban** *(harehare)*: unsere gemeinsame Aufgaben-Übersicht
- [x] **Quick Command Buttons** *(KubrickCode)*: eigene Knöpfe für häufige Git-Befehle
- [x] **GitHub Pull Requests and Issues** *(GitHub)*: Verwaltung von Issues und Pull Requests direkt in VS Code

> **Merksatz:** Extensions installiert man einmal pro Rechner. Nach der Installation erscheinen neue Symbole in der Seitenleiste (das GitHub-Symbol gehört zu *GitHub Pull Requests and Issues*).

## 3. Gemeinsame Kanban-Datei öffnen

Die Klasse arbeitet mit **einer gemeinsamen Kanban-Datei** im Projektordner: einer Datei mit der Endung **`.kanban`**. Das Besondere: Sie ist eine einfache JSON-Datei im Repo – deshalb heißt die Extension „**portables** Kanban", jeder kann sie öffnen, egal wo.

**So öffnest du das Board:**

- [x] Zuerst den Projektordner in VS Code geöffnet haben: **Datei → Ordner öffnen** → Projektordner wählen
- [ ] Frischen Stand holen: unten in der Statusleiste auf das **Sync-Symbol** klicken (oder `git pull` im Terminal)
- [x] Im **Explorer** (Seitenleiste, oberstes Symbol mit den Dateien) die Datei **`board.kanban`** suchen
- [x] Einmal **daraufklicken** (Doppelklick) – das Kanban-Board öffnet sich direkt als bunte Kartenansicht

**Falls nur der JSON-Text erscheint** (statt der Kartenansicht):

- [x] Rechtsklick auf `board.kanban` → **Open With…** → **Portable Kanban** wählen
- [x] Alternativ: Datei offen haben, dann `Strg+Shift+P` → `Portable Kanban` eintippen → den Offer-Eintrag wählen

**Deine eigene Karte anlegen:**

- [x] Im Board auf **`+`** in der Spalte **„To Do"** klicken
- [x] Titel: dein Vorname plus Thema, z. B. `Moritz – Meine Seite`
- [x] Die Karte wird automatisch in der `.kanban`-Datei gespeichert

> **Wichtig:** Das Board ist nur eine Ansicht der Datei. Damit die anderen deine Karte sehen: **speichern** (`Strg+S`) und wie gewohnt **committen und pushen** (die `.kanban`-Datei in `git status` sollte auftauchen). Vor dem nächsten Öffnen immer zuerst **pullen** – sonst überschreibt ihr euch gegenseitig die Karten.

## 4. Ein Issue anlegen

Issues sind die „Aufgabenliste" des Projekts auf GitHub.

- [x] In VS Code: GitHub-Symbol in der Seitenleiste → Bereich **Issues**
- [ ] Oben auf das **+** (*Create Issue*) klicken
- [x] Repository auswählen (das Seminiprojekt)
- [x] Titel: `Meine Seite: <thema>` (plus dein Name)
- [x] Kurze Beschreibung, was du bauen willst
- [x] **Submit / Create Issue**
- [x] Die **Issue-Nummer notieren** (`#nr`) – du brauchst sie später beim Commit

> **Merksatz:** Jede Arbeit im Projekt beginnt mit einem Issue. Wer weiß, *was* getan werden soll, kann besser begründen, *wie* er es tut.

---

## 5. Gist auf GitHub anlegen

Deine privaten Notizen gehören **nicht** ins Klassenprojekt. Du legst deshalb deinen eigenen kleinen „Notizspeicher" bei GitHub an: einen **Gist**. Ein Gist ist ein kleines Mini-Repo für einzelne Dateien, das zu deinem persönlichen Konto gehört.

**Auf github.com:**

- [ ] Einloggen, dann oben rechts auf das **+** (Create new…) klicken → **New gist**
- [ ] Beschreibung eintragen, z. B. `Meine P-Seminar-Notizen`
- [ ] Dateiname vergeben, z. B. `erste_notiz.md`
- [ ] Ein paar Zeilen hineinschreiben (kannst du später ändern)
- [ ] **Secret** auswählen (der Gist erscheint dann in keinem Profil und keiner Suche – nur wer den Link hat, findet ihn)
- [ ] **Create secret gist** klicken
- [ ] Die **HTTPS-Adresse** deines Gists kopieren: Schaltfläche **Code** → HTTPS → kopieren

> **Merksatz:** Du kannst den Gist jederzeit im Browser bearbeiten und alle alten Versionen einsehen. „Secret" heißt aber nicht „privat": Wer den Link kennt, kann mitlesen. Also keine Passwörter oder persönliche Daten hinein.

---

## 6. Gist-Verzeichnis im Projekt anlegen

Jetzt verbindest du den Gist mit deinem Rechner, damit deine Notizen **neben** dem Projekt liegen, aber **nicht im Projekt** landen.

**Im Projektordner (Terminal in VS Code: `Strg+ö`, dann:)**

- [ ] Ordner anlegen:

```bash
mkdir meine_notizen
```

- [x] Deinen Gist hineinklonen *(die HTTPS-Adresse hast du in Schritt 5 kopiert)*:

```bash
cd meine_notizen
git clone <deine-gist-url> notizen
cd ..
```

**Eigene Datei zum Ausprobieren anlegen:**

- [ ] Datei `meine_notizen/notizen/erste_notiz.md` anlegen und etwas hineinschreiben

**Ins externe .gitignore eintragen (wichtigster Schritt):**

- [ ] Datei `.git/info/exclude` im Projektordner öffnen *(das ist die „externe" Git-Ignore, die nur auf deinem Rechner gilt)*
- [ ] Folgende Zeile ergänzen und speichern:

```text
meine_notizen/
```

- [ ] **Kontrolle:** `git status` darf `meine_notizen` nicht mehr anzeigen!

> **Merksatz:** `.git/info/exclude` wirkt wie `.gitignore`, wird aber **nicht mit dem Repo geteilt**. Perfekt für persönliche Ordner, die nur dich etwas angehen.

## 7. Eigenen Ordner im Projekt anlegen

Jeder entwickelt in **seinem eigenen Unterordner** im Projekt-Repo.

- [ ] Down defaults: Auf `main` sein, dann `git pull` (frischen Stand holen!)
- [ ] Im Projekt-Ordner einen neuen Ordner mit deinem Vornamen anlegen:

```bash
mkdir <vorname>
```

*Beispiel:* `moritz`

---

## 8. Eigenen Branch anlegen

Deine Entwicklung läuft auf einem **eigenen Branch**, benannt wie dein Ordner.

- [ ] Branch anlegen und direkt hineinwechseln:

```bash
git checkout -b <vorname>
```

- [ ] Branch ins Remote laden:

```bash
git push -u origin <vorname>
```

- [ ] **Kontrolle:** Unten links in der Statusleiste muss jetzt dein Name stehen, nicht mehr `main`

> (In VS Code geht das auch ohne Terminal: Statusleiste → Branchnamen anklicken → *Create new branch…*)

---

## 9. `meineSeite.py` erstellen

- [ ] Im eigenen Ordner die Datei `meineSeite.py` anlegen: Rechtsklick auf den Ordner → **New File**
- [ ] Eine einfache signalstarke Bäckereiseite als Flask-App schreiben (Gerüst):

```python
from flask import Flask

app = Flask(__name__)

@app.route("/")
def index():
    return "<h1>Hallo vom P-Seminar!</h1><p>Meine erste eigene Seite.</p>"

if __name__ == "__main__":
    app.run(debug=True)
```

---

## 10. Seite bauen (erster Test)

- [ ] Falls noch nicht geschehen, das Projekt als uv-Projekt initialisieren und Flask hinzufügen *(einmalig, siehe Hinweis am Platz)*:

```bash
uv init
uv add flask
```

> **Merksatz:** Wir benutzen **uv** statt `pip`. Pakete werden immer mit `uv add <paket>` installiert – nie mit `pip install`. uv legt automatisch die Datei `pyproject.toml` an und merkt sich alle Pakete darin.

- [ ] Server starten:

```bash
uv run <vorname>/meineSeite.py
```

- [ ] Im Browser `http://127.0.0.1:5000` öffnen – deine Seite muss erscheinen
- [ ] Server mit `Strg+C` wieder stoppen

> **Wichtig:** Bevor du committest, muss der Server gestoppt sein, sonst laufen `debug=True`-Zwischenstände in die Versionsverwaltung.

---

## 11. Pushen

- [ ] Dateien zum Commit vormerken:

```bash
git add <vorname>/
```

- [ ] Commit anlegen – **mit Verweis auf dein Issue** (schließt es automatisch beim Merge!):

```bash
git commit -m "Meine Seite: erste Version (fixes #<nummer>)"
```

- [ ] Hochladen:

```bash
git push
```

- [ ] In VS Code oder auf github.com den **Pull Request** anlegen: *Compare & pull request* → den Mitschüler/den Betreuer als Reviewer eintragen → **Create pull request**

> **Merksatz:** `git add <vorname>/` statt `git add .` – du committest nur deinen eigenen Ordner, niemals den der anderen.

---

## 12. Warten auf den Merge

Deine Arbeit ist jetzt im **Review**.

- [ ] Im GitHub-Panel von VS Code unter **Pull Requests** den Status deines PRs beobachten
- [ ] Falls ein Reviewer Kommentare hinterlässt: auf den eigenen Branch wechseln, Verbesserungen einbauen, committen, pushen – der PR aktualisiert sich automatisch
- [ ] **Warten**, bis gemergt wurde

**Nach dem Merge (alle machen das!):**

- [ ] Zurück auf `main` wechseln:

```bash
git checkout main
```

- [ ] Frischen Stand holen:

```bash
git pull
```

- [ ] Kontrolle: Der Ordner des Mitschülers ist jetzt bei dir sichtbar
- [ ] Auf dem Kanban-Board deine Karte nach **„Fertig"** ziehen
- [ ] Kontrolle: Dein Issue wurde durch `fixes #<nummer>` automatisch geschlossen – nachsehen!
